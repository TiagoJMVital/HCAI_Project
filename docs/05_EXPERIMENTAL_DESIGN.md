# Experimental design

The Project Proposal compares A (Proposer), B (same Proposer with Critic and refinement) and C (learned Learning-to-Defer gate). For a fair A/B comparison, keep the scenario, provider/model, Proposer contract and fixed autonomy rules aligned; B adds only the Critic loop and its mandatory defer when it does not accept. C has not been implemented. Unique run IDs and optional experiment/repetition metadata are recorded by the v2 A/B runners; `eval/compare_runs.py` reads schema `2.0` runs. Historical isolated A/B outputs are engineering checks, not an experimental comparison.

The current B Critic assesses the resulting calendar as well as operations/rationale. This is a documented change to B's Critic input and prompt version; compare runs with different Critic prompt hashes as distinct experimental versions. The resulting calendar is derived by the same deterministic simulator used for validation, not another LLM. Standard A and B runs make **separate stochastic Proposer calls**, so they cannot guarantee an identical initial proposal even with the same provider and prompt. B now has an optional `--initial-proposal-from` input that replays the first structured proposal from a prior schema-2 B run and starts at the current Critic. It records hashes and a source link; subsequent Critic-requested revisions use the normal Proposer. This controls initial-proposal variability for a targeted diagnostic, but does not by itself make A/B comparisons paired: the source must also be linked to the A run, and prompt/model versions, scenario content and protocol must be frozen for a formal experiment. Historical B runs lack a source scenario hash; replay checks their recorded first result calendar against the active scenario simulation when available and records the active scenario hash, but cannot prove all original hidden context was identical.

The subsequent `plausibility_review_v1` policy is a further experimental version. Earlier B runs may include plausibility comments but have no structured revision decision; do not backfill `false` or compare revision rates across versions as if the policies were identical. New B acceptance requires both the unchanged numeric threshold/minimum and an explicit `revision_required=false`. Record the per-iteration numeric outcome, plausibility decision and revision causes. Severity alone does not trigger a revision, and a requested revision does not establish an actual improvement. Evaluate initial versus final scheduling independently and later with human judgments. The Proposer base system prompt, A runner and fixed autonomy rules remain unchanged; B's revision-only instruction now allows retaining operations with a grounded explanation.

Evaluate distinct outcomes: (1) **technical applicability**, including structure and executable hard constraints; (2) **request satisfaction and scheduling quality**, requiring separate objective checks and human review; (3) **rationale quality**, using an independent rubric rather than treating the Critic's own score as ground truth; and (4) **autonomy appropriateness**, against independently adjudicated proposal-level `act/defer` labels. Record errors, deferrals, Critic score trajectories, revisions, latency and costs separately. For C, assess classification and calibration as well as unsafe autonomous actions and unnecessary deferrals. A technically invalid proposal or unacceptable scheduling is not a normal `defer` training case.

Critic plausibility feedback is contextual and uncertain: a zero-minute transition can be acceptable, and unknown location does not prove infeasibility. The model's score cannot replace objective validation, independent request-satisfaction assessment, or human autonomy labels. Store initial/final proposal and per-iteration calendar, validation, feedback and scores to examine what changed. A below-threshold B status is an unresolved Critic review, not a C gate decision.

Freeze scenario families and split before generating labelled examples. All variants and repeated proposals within a family stay together. Use grouped folds only within training families; reserve test families until features, classifier, thresholds and evaluation policy are fixed. A future repeated-run plan should record prompt hashes, provider/model, available generation settings, timestamps and run IDs. LLM nondeterminism means one scenario or one run cannot support general claims. Compare paired A/B results over sufficient families and repetitions; report uncertainty rather than treating the current single imported v2 scenario as evidence.

The active UI shows Critic scores and iterations to reviewers as requested, potentially anchoring their decisions. Before formal annotation, agree whether to keep this visibility or introduce a separate blinded rationale study, and record the choice. Agree on an autonomy rubric and pilot it with training-family proposals only. Do not revise test families based on pilot labels. The present benchmark has too few v2 scenarios, no completed pair of reviews and no C model, so the planned scientific evaluation remains pending.

The Critic is a quality-control reviewer of practical calendar organization, workload and well-being trade-offs. It may request re-evaluation for a concrete, pertinent doubt without requiring proof of material failure. This guidance is identified by the new Critic prompt SHA-256 in each B run while retaining the `plausibility_review_v1` response contract. New runs also retain prior Critic concerns and whether the Proposer changed operations or rationale. Compare prompt hashes before pooling runs. The experimental question is whether Critic intervention improves scheduling and reasoning quality, **not** how many revisions it produces. A revision may keep the same operations, fail to resolve a concern, or even reduce quality; assess these outcomes separately with human review.
